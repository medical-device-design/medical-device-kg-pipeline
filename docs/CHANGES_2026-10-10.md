## 2. What changed

| File | What it does |
|---|---|
| `pipeline/sources/recall_class.py` | **New.** For every recall that is in the recall database but not in the enforcement feed, it reads FDA's own recall page (cfRES, `res.cfm?id=<cfres_id>`). The class is in the page title, e.g. "Class 2 Device Recall …". It writes `ex:recallClassification` ("Class II", the same form the enforcement feed uses) on the **same recall IRI**, plus `ex:recallClassificationSource`, `ex:cfresStatus` and provenance. Fetching starts at most one request per second, with three requests in flight. Pages are cached; a page is fetched again only while its recall is unclassified or not terminated. The contact person and phone number are not ingested. |
| `pipeline/sources/recalls.py` | Keeps reports that FDA posted before numbering, keyed `pending-<event id>-<hash>` and flagged `ex:recallNumberStatus "not yet assigned by FDA"`. The enforcement build is now 40,113 of 40,113. |
| `ontology/shapes/postmarket.shacl.ttl` | A recall number is required unless the record is flagged as not yet assigned (`sh:or`). |
| `ontology/ontology.ttl` | Adds `ex:recallClassificationSource`, `ex:cfresStatus` and `ex:recallNumberStatus`. |
| `scripts/recall_weekly.sh` | **New weekly job on the build VM** (crontab, Mondays 05:30). It refreshes both openFDA recall sources, fetches pages for recalls still missing a class, converts all three to Turtle in `work/out-recalls/`, validates them (riot on every file; SHACL on recalls and recall_class), writes the monitor report and keeps 12 weekly gzipped snapshots. It skips the week if a large build (event, udi or tplc) is running. |
| `scripts/recall_monitor.py` | **New.** Writes `monitor/recalls/<date>/report.md` and `report.json`, plus `recalls.tsv` (one row per recall: number, class, class source, initiated, status), `new_recalls.tsv` and `class_changes.tsv`. It also appends to `monitor/recalls/history.csv`. It warns when built counts fall below FDA's totals, recalls still lack a class, initiation dates are implausible (before 1976 or in the future), or validation fails. |
| `licence_register.csv` | Row added for `recall_class` (FDA public data). |

## 4. Reading the reports without the VPN (`vm-reports` branch)

Cloud runners and cloud scheduled tasks cannot reach the build VM behind the VPN. `scripts/publish_vm_reports.sh` therefore copies the text reports to an orphan branch, **`vm-reports`**, in this repository:

- `recalls/LATEST.md`, `recalls/<date>/` and `recalls/history.csv`, from the recall monitor;
- `health/LATEST.txt`, from the Layer 2 health check.

A Layer 3 digest or a person can then read them from GitHub.

- **It publishes text reports only.** Data, TTL and credentials are never copied.
- **Every published file is redacted, because the repository is public.** The script finds the identifiers at run time (`hostname`, the users in `/home`, `whoami`), so no real name is written in the script itself. Before anything is committed it replaces:
  - the hostname with `build-vm`;
  - every local username with `<user>`;
  - `/home/<anything>` with `~`;
  - credentials file paths (lakeFS env, lakectl config, deploy keys) with `<credentials file>`.
- **A guard then refuses to publish, and exits non-zero,** if any file still contains:
  - the hostname, a local username or a `/home/` path;
  - a private IP (10.x, 172.16–31.x, 192.168.x) or an email address;
  - credential-like text.

  The guard runs on the staged copy and again on the branch copy before the push. `--dry-run DIR` writes the redacted files to a scratch folder without touching git. Publishing is also skipped while `$MDKG/.publish-paused` exists.
- **The first two commits on `vm-reports` (6b5cacd, 91a8f33) were published unredacted.** They showed the VM's hostname, a username, a home path and the lakeFS credentials path; no IPs, passwords or keys. The branch was deleted and recreated as a new orphan holding only redacted files, so those commits are no longer in its history.
- **It pushes with its own deploy key**, `$MDKG/.git-deploy-key-monitor` (ed25519, generated on the VM; the private key never leaves it; mode 600, owned by the PI's account). The key has write access in GitHub's Deploy keys. Without the key the script does nothing.
- **It runs** at the end of `recall_weekly.sh` and from cron on Mondays at 07:15, after the recall run at 05:30 and the health check at 06:30.
- **`vm-reports` is never merged into `main`.**

## 6. Fields that were being dropped, found by a raw-key audit

For each openFDA source, the audit listed every non-empty key path in 20,000 raw records and checked that the module reads it. Two of the gaps were serious.

- **Establishment addresses were empty.** `registrationlisting.py` read `registration.contact_address`, but openFDA puts the address directly on `registration`. Every establishment had lost its street, city, state, ZIP and country, which the geocoder and any "where is this firm" question need. The fix reads both layouts. It also adds the registration expiry year, owner/operator firm and number, US agent **business** name, and 510(k)/PMA links. The listing records (335,765, about 13 per establishment) are now merged, so each of the 25,709 establishments is written once.
- **Device sizes were never ingested in UDI.** These are catheter gauge, length, diameter and so on: 1,837,275 values. UDI also gains the commercial-distribution end date (462,918 devices), GUDID version number and status, package status and discontinue date, the specific PMA supplement that covers a device, and HDE links.

The other gaps were smaller:

- **Recalls (enforcement):** the firm's street address, product type, and `more_code_info`. FDA moves the overflow of long lot lists into `more_code_info`; it is now joined back, so `ex:codeInfo` holds the complete published list.
- **Recalls (recall database):** street address, country, and event-created date.
- **Classification:** summary-malfunction-reporting eligibility, specialty code, and unclassified reason.
- **510(k):** applicant street address and country, review panel, and statement/summary.
- **PMA:** street address, ZIP, and Federal Register notice date.

**Still not ingested, on purpose:** the named people in openFDA. That covers the 510(k) contact, registration official correspondent and US agent person, the recall `additional_info_contact`, and UDI customer phone and e-mail.
