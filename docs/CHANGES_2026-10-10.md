# Changes, 10 October 2026: complete recall layer and weekly recall monitoring

Continues `CHANGES_2026-10-09.md`. Nothing has been published.

## 1. Coverage check before this change

Taken on 2026-10-10 against FDA's live openFDA totals.

| | FDA | Built |
|---|---|---|
| Medical Device Recall database (`device/recall`) | 59,468 | 59,468 |
| Enforcement reports (`device/enforcement`) | 40,113 | 40,112 |
| Distinct recalls after merging | | 59,471 |

**Three gaps were found:**

1. **No recall class for 19,359 recalls (about a third).** The openFDA recall database download carries no Class I/II/III; the class arrived only through the enforcement reports.
2. **One enforcement report was skipped.** FDA posted it before assigning a recall number (event 94520, Medline 30 mL syringes, "Not Yet Classified").
3. **One impossible initiation date.** It reads year 0010, an FDA typo.

## 2. What changed

| File | What it does |
|---|---|
| `pipeline/sources/recall_class.py` | **New.** For every recall that is in the recall database but not in the enforcement feed, it reads FDA's own recall page (cfRES, `res.cfm?id=<cfres_id>`). The class is in the page title, e.g. "Class 2 Device Recall …". It writes `ex:recallClassification` ("Class II", the same form the enforcement feed uses) on the **same recall IRI**, plus `ex:recallClassificationSource`, `ex:cfresStatus` and provenance. Fetching starts at most one request per second, with three requests in flight. Pages are cached; a page is fetched again only while its recall is unclassified or not terminated. The contact person and phone number are not ingested. |
| `pipeline/sources/recalls.py` | Keeps reports that FDA posted before numbering, keyed `pending-<event id>-<hash>` and flagged `ex:recallNumberStatus "not yet assigned by FDA"`. The enforcement build is now 40,113 of 40,113. |
| `ontology/shapes/postmarket.shacl.ttl` | A recall number is required unless the record is flagged as not yet assigned (`sh:or`). |
| `ontology/ontology.ttl` | Adds `ex:recallClassificationSource`, `ex:cfresStatus` and `ex:recallNumberStatus`. |
| `scripts/recall_weekly.sh` | **New weekly job on .83** (crontab, Mondays 05:30). It refreshes both openFDA recall sources, fetches pages for recalls still missing a class, converts all three to Turtle in `work/out-recalls/`, validates them (riot on every file; SHACL on recalls and recall_class), writes the monitor report and keeps 12 weekly gzipped snapshots. It skips the week if a large build (event, udi or tplc) is running. |
| `scripts/recall_monitor.py` | **New.** Writes `monitor/recalls/<date>/report.md` and `report.json`, plus `recalls.tsv` (one row per recall: number, class, class source, initiated, status), `new_recalls.tsv` and `class_changes.tsv`. It also appends to `monitor/recalls/history.csv`. It warns when built counts fall below FDA's totals, recalls still lack a class, initiation dates are implausible (before 1976 or in the future), or validation fails. |
| `licence_register.csv` | Row added for `recall_class` (FDA public data). |

## 3. First run (started 2026-10-10 07:11 on .83)

- Enforcement: 40,113 records, 0 skipped.
- Recall database: 59,468 records.
- Recall pages: 19,350 recalls need a class. The difference from 19,359 comes from duplicate or blank `cfres_id`s. The pages are being fetched at about 60 per minute, so the first pass takes about 5.5 hours. After that, a weekly run fetches only new or still-open recalls.

Final class coverage and validation results go in the first monitor report, `monitor/recalls/2026-10-10/report.md`.
